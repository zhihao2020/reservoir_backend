# Cross-Scale Analysis Design

## 1. Product Architecture Decision

Requirements 1 and 2 are not split into two independent software products.
The project remains one Reservoir Digital Twin Backend with two first-level
functional modules:

```text
Reservoir Digital Twin Backend
├── computational module
│   ├── inversion
│   ├── pressure solver
│   ├── saturation transport
│   ├── capillary / gravity / three-phase
│   └── field fusion
│
├── cross_scale module
│   ├── similarity criteria
│   ├── scale-effect analysis
│   ├── lab-field mapping
│   ├── curve validation
│   └── cross-scale report
│
└── interface layer
    ├── CLI
    ├── YAML
    ├── reports
    └── future UDP bridge
```

The two first-level modules are:

- Module A: Experimental Data Processing and Numerical Computation
- Module B: Cross-scale Analysis and Comparison

This is one backend with two first-level functional modules.

This single-backend architecture is intentional:

1. Cross-scale analysis depends on computational module outputs.
2. Pressure, saturation, production curves, material balance, and reports are
   generated by the computational module.
3. A shared `case_id`, `result_dir`, and report schema simplify the future
   frontend and UDP bridge.
4. Splitting the work into two software products would add data-format,
   communication, deployment, and acceptance-test cost.
5. The MVP should remain one backend project with loosely coupled internal
   modules.

The boundary is strict:

- `cross_scale` can read computational results.
- `cross_scale` must not modify solver internals.
- `cross_scale` must not change reservoir simulation states.
- `cross_scale` only produces mapping, comparison, validation, and reporting
  artifacts.

## 2. Scope

The cross-scale module serves comparisons across:

```text
laboratory experiment scale
→ core / micro-model scale
→ pilot scale
→ field scale
```

The goal is to connect laboratory-scale and field-scale behavior through:

- similarity comparison
- scale-effect analysis
- lab-field mapping
- curve validation
- mechanism interpretation reports

The first version is an engineering MVP. It does not perform commercial-grade
history matching or automatic parameter inversion.

Out of scope for the first version:

- full history matching
- automatic parameter inversion
- Bayesian calibration
- geostatistical upscaling
- corner-point grid upscaling
- commercial simulator coupling
- real-time field data streaming
- black-oil model
- geomechanics
- thermal-reactive transport

## 5. Similarity Criteria Design

The first version should include these dimensionless criteria:

- Reynolds number
- Capillary number
- Peclet number
- Mobility ratio
- Gravity number
- Dimensionless pressure drop
- Dimensionless time

Suggested engineering formulas:

```text
Re = rho * v * L / mu
Ca = mu * v / sigma
Pe = v * L / D
M = lambda_displacing / lambda_displaced
Ng = delta_rho * g * k / (mu * v)
Pi_p = delta_p / pressure_scale
tD = t * v / L
```

Rules:

1. These formulas are engineering approximations.
2. Missing parameters produce warnings rather than silent invalid numbers.
3. All dimensionless numbers enter the report.
4. Dimensionless numbers are not strict proof of similarity; they are
   engineering similarity indicators.

## 6. Scale-Effect Analysis Design

The scale-effect module should analyze:

- geometry scaling
- flow-rate scaling
- pressure-gradient scaling
- capillary-dominated vs viscous-dominated regime
- gravity-dominated regime
- time scaling
- grid-resolution effect

Output fields:

- `scale_ratio_length`
- `scale_ratio_time`
- `scale_ratio_pressure`
- `scale_ratio_flow_rate`
- `regime_lab`
- `regime_field`
- `regime_shift_detected`
- `dominant_force_lab`
- `dominant_force_field`
- `warnings`

Suggested first-version regime rules:

```text
large Ca → viscous-dominated
small Ca → capillary-dominated
large Ng → gravity-dominated
large Pe → convection-dominated
small Pe → diffusion-dominated
```

These thresholds are configurable engineering thresholds, not fixed physical
laws.

## 7. Lab-to-Field Mapping Design

Inputs:

- lab case descriptor
- field case descriptor
- similarity criteria config
- optional measured curves

Outputs:

- `mapped_flow_rate`
- `mapped_pressure_drop`
- `mapped_time`
- `mapped_dimensionless_time`
- `similarity_score`
- `mismatch_metrics`
- `warnings`

The first version does not automatically modify reservoir simulation
parameters. It does not automatically calibrate permeability, porosity, or
relative permeability. It only generates mapping and comparison reports. A
future case generator may consume those reports.

## 8. Experiment-Field Validation Design

Supported curve types:

- production rate
- water cut
- gas fraction
- outlet saturation
- pressure drop
- recovery factor
- cumulative production

First-version mismatch metrics:

- RMSE
- MAE
- MAPE
- R2
- normalized RMSE
- max absolute error
- time-shifted RMSE, planned only

The first version performs curve-to-curve comparison only. It does not perform
automatic history matching, does not optimize parameters, and only outputs a
mismatch report. In short: it does not perform automatic history matching.

## 9. Similarity Score Design

Suggested criterion score:

```text
score_i = exp(-abs(log(x_field / x_lab)))
overall_score = weighted_mean(score_i)
```

Requirements:

- if a criterion is missing, record it as missing
- exclude or down-weight missing criteria according to config
- `overall_score` must remain in `[0, 1]`
- overall_score in `[0, 1]`

The similarity score is an engineering indicator, not strict proof of dynamic
similarity.
