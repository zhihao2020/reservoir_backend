# 1. 项目的真实问题定义

本项目不是普通油藏生产预测软件，也不是单纯的 Darcy 方程求解器。

目标是：

> **针对页岩油相关物理实验的三维多相渗流数字孪生与反演后端。**

实验对象是：

[
300,mm\times300,mm\times300,mm
]

三维立方试块。

试块内部：

* 经过人工构造；
* 可能存在不同填砂区域；
* 可能存在高渗/低渗结构；
* 可能存在倾斜构造；
* 可能存在隔层；
* 可能存在人工裂缝或类似薄层结构；
* 构造可能部分已知，也可能存在不确定性。

试块具有：

* 注入端；
* 采出端；
* 若干内部压力传感器；
* 若干内部饱和度传感器。

实验提供随时间变化的数据，包括但不限于：

* 注入端流量；
* 注入端压力；
* 采出端流量；
* 采出端压力；
* 注入流体组成；
* 产出油/气/水比例；
* 内部测点压力；
* 内部测点饱和度。

最终希望重建：

### 动态状态场

[
p(x,y,z,t)
]

[
S_w(x,y,z,t)
]

[
S_o(x,y,z,t)
]

[
S_g(x,y,z,t)
]

其中：

[
S_w+S_o+S_g=1
]

### 静态物性/结构参数

至少包括：

[
K(x,y,z)
]

以及条件允许时：

[
\phi(x,y,z)
]

进一步可以包括：

* permeability tensor；
* fracture permeability；
* fracture aperture；
* relative permeability parameters；
* capillary pressure parameters；
* structure/facies parameters。

必须严格区分：

**渗透率、孔隙度属于静态物性参数。**

**压力、饱和度属于动态状态。**

饱和度不得再被错误定义为“静态物性场”。

# 2. 最终数字孪生的数学结构

总体模型应该明确表达为：

[
m=
{
K,\phi,
\theta_{kr},
\theta_{pc},
\theta_{frac},
...
}
]

其中 (m) 是静态模型参数。

控制量：

[
u(t)
]

包括：

* injection rate；
* production pressure；
* injection pressure；
* injection composition；
* 其他人为施加的实验控制。

状态：

[
x_t=
[
p_t,S_{w,t},S_{g,t}
]
]

并由：

[
S_o=1-S_w-S_g
]

得到油相饱和度。

正演：

[
x_{0:T}=F(m,u_{0:T})
]

传感器映射：

[
d^{sim}=H(x,m)
]

实验观测：

[
d^{obs}
]

反演：

[
d^{obs}
\rightarrow
m^{posterior}
]

最终系统不是只输出一个 deterministic solution，而应该输出：

[
E[K]
]

[
\sigma_K
]

以及状态场的：

[
E[p],\sigma_p
]

[
E[S_w],\sigma_{S_w}
]

等。

系统必须承认 inverse problem 的非唯一性。

不得把某个单一反演结果包装成“唯一真实地下模型”。

# 3. Controls 与 Observations 必须彻底分开

这是必须审查的重点。

如果实验采用：

[
q_{inj}(t)=specified
]

那么该变量属于：

`Control`

而不是反演误差中的普通 observation。

此时可用于反演的是相应：

[
p_{inj}^{obs}(t)
]

反之，如果：

[
p_{prod}(t)=specified
]

是恒压采出条件，那么：

[
q_{prod}^{obs}(t)
]

才属于 observation。

不得把同一井同一时刻的压力和流量同时作为严格边界条件，然后又拿它们做 history matching。

请建立明确模型：

```text
Controls
Observations
SensorMeasurements
ExperimentalConditions
```

控制条件用于正演。

观测数据用于反演和验证。

# 4. 不能使用普通机器学习随机 train/test 划分

这个项目不是：

```text
random 80% train
random 20% test
```

反演验证应该至少支持三种方式。

## 4.1 空间留出验证

例如 20 个内部测点：

```text
15 assimilation sensors
5 hold-out sensors
```

5 个 hold-out sensor 完全不参与反演。

posterior model 必须预测这些位置。

---

## 4.2 时间外推验证

例如：

```text
0–60 min
```

用于 history matching。

```text
60–100 min
```

完全用于 forward prediction。

模型在 60 min 后不得再用未来 observation 修正参数。

---

## 4.3 Synthetic truth

必须具有完整 synthetic inversion benchmark：

先人工定义：

[
K_{true}
]

例如：

* layered case；
* high-perm channel；
* low-perm barrier；
* anisotropic case；
* fractured case。

正演生成 synthetic sensor measurements。

加入已知噪声。

然后使用 inverse pipeline 进行反演。

因为真实实验中的真实 3D K 不可直接知道，所以 synthetic truth 是反演算法验证的核心。

# 27. 反演误差不能只使用普通 MSE

应支持：

[
J=
r^TR^{-1}r
]

其中：

[
r=d^{obs}-d^{sim}
]

(R) 为 measurement error covariance。

不同类型传感器：

* pressure；
* flow；
* saturation；

量纲和噪声水平完全不同。

不得直接拼接原始数值然后计算普通 MSE。

```text
strong nonlinear batch inverse problem
```

或 ES-MDA 明显收敛困难的问题。

---

## EnKF

用于：

```text
online state assimilation
```

即实时 digital twin。

第一阶段必须至少完整实现 ES-MDA。

其他算法如果当前没有实现，应留下清晰接口和 roadmap，但不要留下虚假空壳类。

---

# 31. 简单的 Assimilation Planner

不要引入 AI agent 自动选算法。

第一版使用明确规则即可：

```text
batch static parameter inversion
    -> ESMDA

batch + strong nonlinearity / poor convergence
    -> IES candidate

streaming observation / state correction
    -> EnKF
```

Planner 只承担显式 routing。

不要过度智能化。

```text

```

# 41. 内部统一使用 SI

所有 physics core 必须使用 SI：

```text

s

```

输入文件可以使用：

```text

```

但必须在 IO 边界完成转换。

不得在 solver 内部混合：


# 42. 数组规范必须统一

选择并文档化唯一 field convention。

推荐：

```text

    (n_cells,)

    (n_cells, n_components)
```

不要不同模块分别使用：

```text

(nz, ny, nx)
(n_cells,)
```

却没有统一 mapping。

Cartesian reshape 必须由 grid helper 处理。

# 43. 不允许隐式 global state

Case、grid、fluid、rock、controls、observations 应明确传递。

禁止：

* module-level mutable config；
* hidden singleton；
* 隐式当前网格；
* 隐式当前 fluid。

这对 ensemble 并行尤其重要。

---

# 44. Ensemble forward 必须支持并行

每个 ensemble member 本质独立。

架构应该允许：

```text
serial
process pool
```

至少两种 execution backend。

第一阶段 CPU multiprocessing 即可。

不要第一阶段引入 GPU 框架。

并行结果必须在固定 random seed 下可重复。

---

# 45. 必须考虑缓存

可缓存：

* grid geometry；
* topology；
* observation mapping；
* fixed structural matrices。

但如果 K 改变导致 transmissibility 改变，不得错误复用旧 transmissibility。

缓存必须有明确 invalidation 条件。

# 46. Forward Solver 的验证要求

必须建立以下 benchmark。

## Single phase

### 1D analytical pressure

验证：

* pressure；
* flux；
* conservation。

### 2D/3D homogeneous flow

验证：

* boundary；
* source/sink；
* flux consistency。

### anisotropic K

检查 tensor permeability。

---

# 47. Two-phase 验证

至少：

### Buckley-Leverett

无毛管、无重力场景。

比较：

* front location；
* saturation profile；
* water cut。

### mass conservation

检查：

[

]

与 boundary/source flux。

### saturation bounds

必须保证：

[
0\le S\le1
]

---

# 48. Capillary 验证

至少检查：

* Pc 单调性；
* equilibrium；
* capillary diffusion；
* endpoint behavior。

---

# 49. Three-phase 验证

至少：

* saturation closure；
* phase disappearance；
* phase mobility；
* phase rate；
* global conservation；
* timestep stability。

如果当前代码做不到，不得宣称 three-phase complete。

---

# 50. Grid 验证

必须检查：

```text
300 mm / 10 mm -> 30³
```

以及：

* cell volume；
* total block volume；
* face orientation；
* neighbors；
* boundary identification。

总 volume 必须正确恢复：

[

]

---

# 51. Sensor Observation 验证

建立已知解析场：

[

]

检查任意 sensor coordinate interpolation 是否正确。

对于 volume sensor：

检查体积平均结果。

不能只测试恰好位于 cell center 的 sensor。

# 52. Inversion 最小数学 benchmark

必须建立 linear-Gaussian inverse problem。

在具有解析 posterior 的问题上检查 ensemble update 是否合理。

这比直接拿复杂 reservoir case 测 ES-MDA 更重要。

```text
posterior K error

posterior prediction

posterior variance
```

* true model 位于合理 posterior 范围。

# 58. Ensemble forward failure 必须处理

某些 realization 可能因为：

* 极端 K；
* solver 不收敛；
* timestep 失败；

导致 forward failure。

不能：

```text
NaN -> covariance
```

直接污染整个 ensemble。

需要明确策略：

* retry smaller dt；
* reject invalid parameter；
* regenerate member；
* mark failed member；
* abort if failure ratio exceeds threshold。

该策略必须可配置且有日志。

# 83. 最重要的验收标准

最终项目不能再被描述成：

> 一个包含压力、饱和度、反演、融合等很多功能的 reservoir backend。

它必须形成一条完整、可验证的科学计算链：

[
\boxed{
\text{Experiment}
\rightarrow
\text{Controls}
\rightarrow
\text{Prior Model}
\rightarrow
\text{Multiphase Forward Solver}
\rightarrow
\text{Observation Operator}
\rightarrow
\text{Data Mismatch}
\rightarrow
\text{Ensemble Assimilation}
\rightarrow
\text{Posterior Model}
\rightarrow
\text{Forecast}
}
]

对于真实的 300 mm 页岩油相关实验，最终必须能够回答：

1. 当前采用了什么物理假设？
2. 注入和采出条件是什么？
3. 哪些数据参与了反演？
4. 哪些数据被保留用于验证？
5. K 是如何参数化的？
6. 为什么当前数据可以或不可以识别这些参数？
7. forward solver 是否质量守恒？
8. posterior 是否比 prior 更能预测未参与反演的数据？
9. 哪些区域的 K 被传感器真正约束住了？
10. 哪些区域仍具有巨大 uncertainty？
11. 新数据到来后 digital twin 如何更新？
12. 如果模型预测失败，是物理模型问题、参数问题、网格问题还是观测问题？

只要其中多数问题当前代码无法回答，就说明项目还没有真正形成数字孪生反演后端。

# 84. 代码风格最后要求

本项目当前仍处于绿地阶段。

请大胆删除错误设计。

要求：

```text
simple
explicit
testable
physical
numerically conservative
modular but not over-engineered
```

优先使用普通、清晰的 Python。

不要为了展示“高级架构”使用复杂元编程。

不要为了兼容历史实现污染新接口。

不要保留已无实际用途的 legacy code。

不要通过 mock 大量 physics behavior 让测试通过。

测试必须验证真实 numerical behavior。

不要声称尚未实现的能力已经实现。

最终目标不是代码量最大，而是：

> 用尽可能清晰、可靠的架构，把“实验数据 → 三维多相正演 → 观测映射 → ensemble 反演 → 不确定性 → 预测”这条核心链真正打通。
