# Validation

This document explains the validation structure and report locations. Module
status is maintained only in [../STATUS.md](../STATUS.md).

## Test Layers

The test suite is organized around:

- unit tests for grids, fields, units, wells, and low-level numerical helpers;
- module tests for pressure, velocity, transport, relperm, inversion, fusion,
  and cross-scale utilities;
- benchmark hardening tests that check report schemas, numerical sanity, and
  non-claim wording;
- integration tests for data ingestion, result export, project/case registries,
  performance reports, and simplified sequential simulation.

Run the full suite with:

```bash
pytest -q
```

For a narrower check, run the relevant test file directly, for example:

```bash
pytest tests/test_pressure_solver_benchmark_hardening.py -q
pytest tests/test_saturation_transport_benchmark_hardening.py -q
pytest tests/test_result_export_contract.py -q
```

This documentation cleanup did not rerun the full suite.

## Report Locations

Generated validation and benchmark artifacts are stored under:

- `accuracy_reports/`: JSON and Markdown summaries generated by benchmark,
  enhancement, fusion, cross-scale, performance, project/case, and simulation
  report runners.
- `validation_reports/`: optional local validation output directory if present
  in a checkout.

Common report families include:

- `pressure_solver_*summary.*`
- `saturation_transport_*summary.*`
- `capillary_gravity_benchmark_summary.*`
- `three_phase_benchmark_summary.*`
- `parameter_fusion_*summary.*`
- `benchmark_registry_summary.*`
- `performance_baseline_summary.*`
- `impes_loop_summary.*`
- `fusion_synthetic_twin_summary.*`

## Benchmark Registry

The benchmark registry reads existing summary files and indexes:

- benchmark name;
- module association;
- validation category;
- reference type;
- key metrics;
- report paths;
- limitations and non-claim checks.

It does not rerun physics cases or replace module-level reports.

## Reference Data Policy

Open-source reference materials under `references/` are used as adapted
metadata or method context. They are not runtime dependencies, and they do not
create equivalence with OPM Flow, MRST, SPE decks, or commercial simulators.

## Rerun Guidance

Use targeted tests while editing one subsystem. Use `pytest -q` before claiming
repository-wide regression health. If a documentation-only cleanup does not
rerun tests, state that explicitly in the change report.
